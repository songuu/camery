## 0. 一句话

**采集交给你现有的工具（Codex、GrokBot、Muse……），Camery 只做"收、归、评、用"。**

各采集器每天定时去红果、NetShort、X 等平台找热点，按统一格式推送到 Camery 的公共入口。Camery 负责：
- 校验和去重；
- 把不同平台上的同一部剧、同一个梗合并起来；
- 打分，生成每日简报；
- 直接用到立项、选题和反同质化检查上。

```
 Codex ─┐                     ┌─► 每日热点简报（制片收件箱）
GrokBot ┼─► 公共入口 ─► 归并 ─► 评分 ─┼─► 选题池 → 一键立项
  Muse ─┤   (HTTP/MCP/文件)  (去重/聚类)  ├─► 立项反同质化检查
  其他 ─┘                     └─► 题材档案 / 俗套库更新建议
```

为什么采集不由平台自己做：
- 各平台的反爬策略和接口变化很快，用户手上的工具更灵活；
- 换工具、加平台都不需要改 Camery；
- 采集行为发生在用户自己的账号和工具里，平台方的服务条款由采集方自负，Camery 只接收结构化结果。

## 1. 公共入口

### 1.1 三种接入方式，同一份数据格式

| 方式 | 适合 | 说明 |
|---|---|---|
| **HTTP 推送** | GrokBot、脚本、定时任务 | `POST /api/v1/intake/signals`，批量推送 |
| **MCP 工具** | Codex、Claude 等 Agent 型采集器 | `camery.submit_trend_signals`，与 HTTP 同一套 schema；Agent 采集完直接调用 |
| **文件投递** | 离线环境、手工整理 | JSON/CSV 经同一服务导入；监听目录绑定租户及采集器，界面上传检查当前用户权限 |

### 1.2 推送格式 `camery.trend-signal/v1`

```jsonc
POST /api/v1/intake/signals
Authorization: Bearer <采集器令牌>
Idempotency-Key: grokbot-01:2026-11-10:morning      // 重复推送不会重复入库
X-Camery-Signature: sha256=<HMAC(body)>              // 可选，防篡改

{
  "schema": "camery.trend-signal/v1",
  "collector": { "id": "grokbot-01", "tool": "grokbot", "run_id": "2026-11-10T08:00+08:00" },
  "captured_at": "2026-11-10T08:05:12+08:00",
  "signals": [
    {
      "platform": "hongguo",                 // hongguo | netshort | x | douyin | kuaishou | reelshort | dramabox | other
      "region": "CN", "language": "zh",
      "kind": "ranking_entry",               // drama | ranking_entry | topic | trope | creator_post | news
      "title": "某某剧名",
      "url": "https://...",                  // 必填：可回溯的来源
      "external_id": "平台内ID，可空",
      "rank": { "list": "热播榜", "position": 3, "list_size": 50 },
      "metrics": [
        { "name": "heat", "value": 98234, "unit": "platform_heat",
          "definition": "平台热度值，不等于播放量" }   // 每个数字必须说明口径
      ],
      "tags": ["重生", "复仇", "豪门"],
      "summary": "用采集器自己的话写的剧情/话题概要，≤500 字",
      "hooks": ["开场被当众退婚", "第 1 集结尾身份揭一半"],
      "evidence": { "quote": "≤100 字原文引用，可空", "screenshot_ref": null },
      "confidence": 0.7                      // 采集器对这条信息的把握
    }
  ]
}
```

**响应**：逐条返回 `accepted / duplicate / rejected(原因)`。部分失败不影响其他条目。

令牌确定租户与采集器身份，不能以请求体冒认。幂等键在租户/采集器内唯一：相同请求重放原逐条结果，相同键不同请求体报冲突。`dry_run` 不写业务数据也不消费幂等键。令牌只存哈希，可选 HMAC 不能替代鉴权；具体签名算法、编码和轮换方式在接入协议定稿时明确。

### 1.3 入口规则

| 规则 | 原因 |
|---|---|
| 每个采集器一个令牌，可单独吊销；令牌绑定租户和允许的平台 | 一个采集器出问题不影响其他采集器 |
| `url`、`captured_at`、`collector` 必填；URL 只作来源引用，入口不任意抓取 | 每条热点都能追到来源和时间，避免来源链接触发非预期网络请求 |
| 数字必须带口径（热度 / 播放 / 点赞 / 排名） | 不同平台、不同口径的数字不能直接比较 |
| 只收概要、标签、钩子和不超过 100 字的引用，不收剧本全文、视频文件 | 版权：我们只要情报，不囤内容 |
| 推送内容一律当作**不可信数据** | 防提示注入：概要里写的"指令"只当文字 |
| 限流 + 单批上限（如 500 条） | 防采集器故障刷爆 |
| 格式版本化（`v1`），旧版本保留兼容期 | 采集器可以慢慢升级 |

### 1.4 私有化部署怎么收推送

Studio 主打私有化，服务器通常在客户内网，外部采集器推不进去。提供三种方式：

| 方式 | 做法 |
|---|---|
| 采集器也在内网 | 直接推内网地址（最简单） |
| **云端中继（1.5 可选）** | 采集器推到 Camery 云端的租户专属信箱，私有化实例定时主动拉取。只出不进，不需要客户开放端口 |
| 文件投递 | 采集器把结果写到共享目录，实例监听导入 |

1.0 使用内网直推、MCP 或文件；完全离线无需云端依赖。1.5 中继只暂存热点数据，按租户隔离，确认消费后保留 7 天即删；拉取/确认幂等，断网恢复不重复消费，未确认及死信的最长保留期在实现前配置并向管理员展示。

## 2. 归并与评分

### 2.1 三层数据

| 层 | 实体 | 内容 |
|---|---|---|
| 原始 | `TrendSignal` | 每个采集器每次推送的原样记录，不改动，可审计 |
| 归并 | `TrendItem` | 跨平台、跨采集器合并后的"一部剧 / 一个话题 / 一个梗"，带别名与来源列表 |
| 产出 | `TrendDigest` | 每日简报；`TopicIdea` 选题卡 |

### 2.2 归并（研究 Agent 负责）

- **同一部剧**：先按 `platform + external_id`、URL 精确匹配，再按标题 + 简介做相似度匹配，最后由 LLM 确认。可能匹配错的条目进入"待确认"，不自动合并。
- **同一个梗**：把标签和钩子映射到我们的题材体系（GenreProfile、开头钩子 5 类、卡点 6 类、俗套库条目）。这样"红果上的重生复仇剧"和"X 上讨论的 revenge rebirth drama"能落到同一个梗上。
- **出海标记**：NetShort、ReelShort 等海外平台的条目保留地区和语言，为出海版选题预留。

精确匹配识别的是同一 TrendItem，不删除不同时间的观测。`platform + external_id` 或规范化 URL 相同但采集日期、排名变化时保留新 TrendSignal；批次重放不会重复写入。原始观测不可变，归并结果保留证据映射；相似归并及题材映射在 1.5，疑似匹配需人工确认。

### 2.3 评分

各平台的数字口径不同，不直接相加，而是先在**平台内、榜单内**标准化，再合并：

| 指标 | 算法 | 用途 |
|---|---|---|
| 热度 | 平台内排名百分位 | 现在有多热 |
| 势头 | 7 日排名变化 | 正在起来还是在退 |
| 扩散 | 出现在几个平台、几个采集器 | 是不是全网都在热 |
| 饱和度 | 近 30 天同梗条目数 | 供给是否过剩（红海） |
| AI 适配 | 题材是否真人难拍（修仙、末世、玄幻 +）；可拍性风险（打斗、群戏 −） | 用 AI 做是否划算 |
| 可信度 | 采集器置信度 × 来源数 | 单一来源的条目降权 |

阶段判定：**蓝海**（热度上升、饱和度低）/ **将红** / **红海** / **衰退**，沿用 OnlyShot 的四分法。权重可配置，并用后续立项结果回调。

完整评分属 1.5，1.0 只做带来源/日期的规则排序。计算须保留榜单、口径、日期、公式与权重；缺少 7 日历史就不输出势头，覆盖不足时不判阶段。采集器置信度仅是自评输入；同源转载不能简单算多个独立来源，展示缺数和不确定性。

## 3. 怎么用起来

| 产出 | 内容 | 谁用 |
|---|---|---|
| **每日热点简报** | 每天固定时间进入制片收件箱：Top 10 上升梗、新上榜剧、衰退信号、与在做项目撞车的提醒；每条附来源链接和日期 | 制片、编剧 |
| **选题池** | 把热点转为选题卡：只借机制（配方、钩子、节奏），人物和设定全部原创；附"同类已有作品"清单 | 开发 Agent、编剧 |
| **一键立项** | 选题卡 → 新项目，自动带入题材配方、反同质化约束（"不能这么写"清单） | 立项向导 |
| **反同质化检查** | 立项和剧本阶段，与近 30 天热点比对；和 3 部以上撞车时给出差异化角度 | 审片 Agent |
| **题材档案更新建议** | 节奏参数、流行梗变化 → 生成 GenreProfile 和俗套库的修改建议，**人工审批后生效** | 方法包维护者 |
| **问答** | "最近重生题材在红果怎么样？" 由研究 Agent 基于热点库回答，附来源 | 所有人 |
| **知识工坊** | X 等平台上的科普话题同样进入雷达，作为工坊的选题建议 | 个人创作者 |

每日简报按租户时区运行，租户/日期/配置版本唯一，重启续跑不重复投递；无新数据明确提示，不能沿用旧简报冒充当日情报。上述产出按第 7 节分期，1.0 反同质化用于立项与剧本，1.5 再开放来源问答和增强选题。

## 4. Agent 分工

| Agent | 职责 |
|---|---|
| 研究 Agent（新增"情报"能力） | 归并、映射题材体系、评分、写每日简报、回答问答 |
| 开发 Agent | 把热点转成原创选题卡；立项时做反同质化 |
| 审片 Agent | 剧本阶段的撞车检查 |
| 制片 Agent | 把简报和需要拍板的选题推进收件箱 |

1.0 研究 Agent 先处理精确归并与规则简报，开发/审片做反同质化；相似归并、题材映射、完整评分、选题卡、问答随 1.5 启用。原始接收与排序由确定性服务执行，Agent 处理解释与建议。

所有对题材档案、俗套库的修改都只是候选，需要人工采用。

## 5. 采集器接入包

为了让 Codex、GrokBot、Muse 等工具快速接入，提供一个接入包：

- 格式说明 + JSON Schema（`trend-signal.v1.schema.json`）；
- `curl` 示例和一个最小 Python/Node 推送脚本；
- MCP 服务配置示例（给 Codex 等 Agent 型工具）；
- **采集指令模板**：一段可直接交给 Agent 型采集器的提示词，规定要采哪些平台和榜单、每个字段怎么填、数字口径怎么写、只写概要不抄全文；
- 自检工具：`POST /api/v1/intake/signals?dry_run=true` 只校验不入库，返回逐条问题。

Muse 的具体工具及输出能力尚未知：先提供通用 JSON/CSV 文件映射，HTTP/MCP 支持核实后再配置；不新增未验证的专属连接器。

采集器状态页：每个采集器最近一次推送时间、条数、拒收率。连续 2 天没有推送就提醒。

## 6. 合规边界

- 采集行为发生在用户的工具和账号里，平台服务条款由采集方遵守；Camery 记录每条数据的来源和采集方式，**不提供绕过平台限制的采集功能**。
- 只存元数据、概要和短引用；不存视频、剧本全文、截图原图（截图只存引用）。
- 选题卡只借机制，不复刻已有作品的人名、设定和桥段（与参考调研的原则一致）。
- 热点数据带日期，超过 30 天的条目在简报和问答中标注"过期"。
